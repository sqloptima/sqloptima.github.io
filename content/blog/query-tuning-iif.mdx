Dummy guide: `IIF(condition, true_value, false_value)` is syntactic sugar over a simple `CASE`.

Reach for `IIF` when you need a one-line flag or display value in a select list. Prefer explicit
`CASE` when there are more than two branches, nested conditions, or when the expression is part
of a persisted computed column that teammates must maintain.

Remember `IIF` still evaluates like `CASE` for type precedence — mismatched types will coerce,
sometimes in surprising ways. Check the output type in the plan or with `SQL_VARIANT_PROPERTY`
when mixing numerics and strings.

## Why conditional expression tuning deserves a method

The central principle is that IIF compiles as a CASE expression, so the real question is how conditional logic affects estimates, types, and access paths. A single metric, recommendation, or successful command is not enough. The decision has to connect an observed symptom to a plausible cause, a controlled change, and a result that can be verified under the workload that matters.

## Evidence to collect

Use evidence from the same time window whenever possible:

- implicit conversion and result data type
- expression placement in predicates
- estimated versus actual rows
- repeated scalar evaluation

## A practical workflow

1. Expand the expression mentally as CASE.
2. Check type precedence and NULL behavior.
3. Move functions away from indexed columns when possible.
4. Measure the final query rather than the expression alone.

## Common mistakes

Avoid these shortcuts:

- blaming syntax without reading the plan
- changing NULL semantics
- assuming a shorter expression executes faster

## Verification and completion

Define completion before making the change. Confirm correctness first, then compare latency, throughput, reads, CPU, waits, storage behavior, or recovery time as appropriate for **Using IIF for simple conditional expressions**. Test negative and boundary cases, not only the path expected to succeed. Watch the system long enough to cover the relevant workload pattern.
