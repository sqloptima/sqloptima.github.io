Autogrowth is a safety net, not a capacity plan.

If growth events cluster during business hours, pre-size files and fix the workload that forces
sudden expansion. Monitoring should surface growth cadence next to latency spikes.

## Why file growth deserves a method

The central principle is that autogrowth is an emergency safety mechanism, not a capacity-management strategy. A single metric, recommendation, or successful command is not enough. The decision has to connect an observed symptom to a plausible cause, a controlled change, and a result that can be verified under the workload that matters.

## Evidence to collect

Use evidence from the same time window whenever possible:

- growth events and duration
- free space in data and log files
- underlying volume capacity and latency
- log reuse waits and transaction behavior

## A practical workflow

1. Baseline file size and growth history.
2. Choose fixed growth increments.
3. Pre-size files for the forecast workload.
4. Alert before both database and volume space become critical.

## Common mistakes

Avoid these shortcuts:

- percentage-based growth
- tiny growth increments
- monitoring the file but not its volume

## Verification and completion

Define completion before making the change. Confirm correctness first, then compare latency, throughput, reads, CPU, waits, storage behavior, or recovery time as appropriate for **Autogrowth events are silent outages**. Test negative and boundary cases, not only the path expected to succeed. Watch the system long enough to cover the relevant workload pattern.

### Before you run it

- Run the script first on a non-production or read-only connection when possible.
- Review the complete SQL file before execution and confirm that the connected instance is the intended target.
- Required access: VIEW SERVER STATE plus visibility into the target databases.
- Open SQL Server Management Studio or Azure Data Studio, connect to the instance, open the downloaded file, and select **Execute**. Do not run diagnostic scripts through an application login.
- Save the result grid with the server name, collection time, and incident window. DMV output changes over time and often resets after a SQL Server restart.

### What the script does

Inventories data and log files, allocated and used space, free space, growth settings, and warning status across selected user databases. The download is intended for diagnosis and does not apply an automatic remediation. Read every statement anyway, especially when adapting the script for automation or a different SQL Server version.
