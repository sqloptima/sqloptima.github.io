Most “mystery” production issues are decisions made on install day: too few TempDB files, CTFP left at 5, max memory set to the whole box, Instant File Initialization skipped, or Query Store never enabled.

A gated installation checklist turns those into explicit yes/no steps before the first user database lands.

## What the checklist forces you to decide

- Storage layout and formatting before setup runs
- Service accounts and least-privilege permissions
- Memory, MAXDOP, and cost threshold for parallelism
- TempDB sizing, equal files, and growth policy
- Backup compression, maintenance, Agent jobs, and alerts
- Security surface area, protocols, and monitoring baseline

## Why production installation deserves a method

The central principle is that a production SQL Server install should encode workload, security, storage, recovery, and support decisions before users arrive. A single metric, recommendation, or successful command is not enough. The decision has to connect an observed symptom to a plausible cause, a controlled change, and a result that can be verified under the workload that matters.

## Evidence to collect

Use evidence from the same time window whenever possible:

- service accounts and privileges
- data, log, tempdb, and backup storage
- memory, MAXDOP, and cost threshold
- patch level, encryption, backup, and monitoring

## A practical workflow

1. Document requirements and ownership.
2. Install and patch with repeatable settings.
3. Apply security and performance baselines.
4. Test backup, restore, monitoring, and connectivity.

## Common mistakes

Avoid these shortcuts:

- accepting setup defaults
- placing every file on one volume
- going live before restore and alert tests

## Verification and completion

Define completion before making the change. Confirm correctness first, then compare latency, throughput, reads, CPU, waits, storage behavior, or recovery time as appropriate for **A production SQL Server install checklist that survives audits**. Test negative and boundary cases, not only the path expected to succeed. Watch the system long enough to cover the relevant workload pattern.

### Before you run it

- Review every statement and confirm the connection points to the intended SQL Server database server.
- Run through a non-production or read-only diagnostic account first when possible.
- Required access: VIEW SERVER STATE and visibility into server configuration.
- Save the output with the server name, database name, collection time, and workload window so another engineer can reproduce the analysis.

### What it does

Reports important instance settings and compares them with operational review guidance. The script is diagnostic and does not apply an automatic remediation. Result values still need workload context, a second supporting signal, and a before-and-after comparison.
