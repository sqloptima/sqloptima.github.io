Dummy guide: index maintenance should follow fragmentation and page density, not a fixed calendar.

Reorganize when fragmentation is moderate and the index is large enough that a full rebuild blows
the window. Rebuild when the leaf level is badly fragmented *and* you have the I/O budget (or can
use online rebuilds on Enterprise / Azure SQL tiers that support it).

Always exclude tiny indexes and heaps that never grow — maintenance churn there wastes log and
tempdb without improving reads.
