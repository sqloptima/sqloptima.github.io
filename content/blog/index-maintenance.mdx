Dummy guide: index maintenance should follow fragmentation and page density, not a fixed calendar.

Reorganize when fragmentation is moderate and the index is large enough that a full rebuild blows
the window. Rebuild when the leaf level is badly fragmented *and* you have the I/O budget (or can
use online rebuilds on Enterprise / Azure SQL tiers that support it).

Always exclude tiny indexes and heaps that never grow — maintenance churn there wastes log and
tempdb without improving reads.

## Why index maintenance deserves a method

The central principle is that maintenance should solve measured problems without creating unnecessary logging, blocking, or replica lag. A single metric, recommendation, or successful command is not enough. The decision has to connect an observed symptom to a plausible cause, a controlled change, and a result that can be verified under the workload that matters.

## Evidence to collect

Use evidence from the same time window whenever possible:

- fragmentation and page density
- statistics freshness
- index usage and size
- log throughput and HA queue growth

## A practical workflow

1. Classify indexes by size and workload role.
2. Prioritize statistics when estimates are the issue.
3. Schedule only justified rebuilds or reorganizations.
4. Track duration, log generation, and query behavior.

## Common mistakes

Avoid these shortcuts:

- treating rebuilds as general tuning
- maintaining unused indexes
- running heavy work without HA awareness

## Verification and completion

Define completion before making the change. Confirm correctness first, then compare latency, throughput, reads, CPU, waits, storage behavior, or recovery time as appropriate for **Index maintenance that fits the maintenance window**. Test negative and boundary cases, not only the path expected to succeed. Watch the system long enough to cover the relevant workload pattern.

### Before you run it

- Run the script first on a non-production or read-only connection when possible.
- Review the complete SQL file before execution and confirm that the connected instance is the intended target.
- Required access: VIEW DATABASE STATE.
- Open SQL Server Management Studio or Azure Data Studio, connect to the instance, open the downloaded file, and select **Execute**. Do not run diagnostic scripts through an application login.
- Save the result grid with the server name, collection time, and incident window. DMV output changes over time and often resets after a SQL Server restart.

### What the script does

Provides the physical evidence needed to decide whether an index needs reorganizing, rebuilding, statistics attention, or no maintenance. The download is intended for diagnosis and does not apply an automatic remediation. Read every statement anyway, especially when adapting the script for automation or a different SQL Server version.
