Distributed traces tell you which service slowed down. They do not explain latch contention.

Keep database-native telemetry first-class: waits, plans, IO stalls, and lock graphs. Then correlate
with traces when the path crosses app tiers.

## Why database observability deserves a method

The central principle is that useful observability connects a user symptom to database workload, resource pressure, and change history. A single metric, recommendation, or successful command is not enough. The decision has to connect an observed symptom to a plausible cause, a controlled change, and a result that can be verified under the workload that matters.

## Evidence to collect

Use evidence from the same time window whenever possible:

- service latency and errors
- database waits and saturation
- query and plan history
- deployments, configuration, and maintenance events

## A practical workflow

1. Define the questions operators need to answer.
2. Collect signals with consistent identity and time.
3. Correlate symptoms with workload and change events.
4. Turn repeated investigations into dashboards and alerts.

## Common mistakes

Avoid these shortcuts:

- collecting metrics without retention context
- building dashboards with no operational question
- separating application and database timelines

## Verification and completion

Define completion before making the change. Confirm correctness first, then compare latency, throughput, reads, CPU, waits, storage behavior, or recovery time as appropriate for **Observability for DBAs is still SQL-shaped**. Test negative and boundary cases, not only the path expected to succeed. Watch the system long enough to cover the relevant workload pattern.

### Before you run it

- Run the script first on a non-production or read-only connection when possible.
- Review the complete SQL file before execution and confirm that the connected instance is the intended target.
- Required access: VIEW SERVER STATE.
- Open SQL Server Management Studio or Azure Data Studio, connect to the instance, open the downloaded file, and select **Execute**. Do not run diagnostic scripts through an application login.
- Save the result grid with the server name, collection time, and incident window. DMV output changes over time and often resets after a SQL Server restart.

### What the script does

Captures a point-in-time set of workload, waits, sessions, resource, and configuration signals for a repeatable diagnostic baseline. The download is intended for diagnosis and does not apply an automatic remediation. Read every statement anyway, especially when adapting the script for automation or a different SQL Server version.
