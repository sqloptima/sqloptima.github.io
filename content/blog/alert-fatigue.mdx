Noise alerts train engineers to ignore the console.

Page on user-impacting symptoms: sustained latency, blocking chains, failed restores. Keep
informational metrics on dashboards. Every alert should name an owner and a next step.

## Why alert quality deserves a method

The central principle is that alerts should represent conditions that require timely human action. A single metric, recommendation, or successful command is not enough. The decision has to connect an observed symptom to a plausible cause, a controlled change, and a result that can be verified under the workload that matters.

## Evidence to collect

Use evidence from the same time window whenever possible:

- sustained user-facing latency
- blocking that exceeds the workload threshold
- failed backup or restore verification
- replica or availability risk

## A practical workflow

1. Assign an owner and severity.
2. State the evidence and affected service.
3. Link a tested runbook.
4. Review noisy rules after every incident.

## Common mistakes

Avoid these shortcuts:

- paging on every threshold breach
- alerts without a next action
- duplicate notifications from several tools

## Verification and completion

Define completion before making the change. Confirm correctness first, then compare latency, throughput, reads, CPU, waits, storage behavior, or recovery time as appropriate for **Alert fatigue destroys on-call trust**. Test negative and boundary cases, not only the path expected to succeed. Watch the system long enough to cover the relevant workload pattern.
