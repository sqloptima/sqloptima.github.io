The statement that timed out is frequently a victim, not the root cause.

When `LCK_*` waits rise, identify the head of the blocking chain and the transaction that holds it.
Tools that only list slow queries without blockers send teams down the wrong rabbit hole.

## Why blocking analysis deserves a method

The central principle is that the head blocker matters more than the longest list of waiting sessions. A single metric, recommendation, or successful command is not enough. The decision has to connect an observed symptom to a plausible cause, a controlled change, and a result that can be verified under the workload that matters.

## Evidence to collect

Use evidence from the same time window whenever possible:

- lead blocker session and open transaction
- wait duration and lock resource
- executing statement and transaction age
- application name, host, and affected requests

## A practical workflow

1. Capture the blocking chain before intervening.
2. Identify the transaction owner.
3. Choose the least disruptive resolution.
4. Correct the query, transaction scope, or access pattern.

## Common mistakes

Avoid these shortcuts:

- killing an arbitrary waiting session
- using NOLOCK as a universal fix
- ignoring application transaction boundaries

## Verification and completion

Define completion before making the change. Confirm correctness first, then compare latency, throughput, reads, CPU, waits, storage behavior, or recovery time as appropriate for **Blocking chains beat single-query blame**. Test negative and boundary cases, not only the path expected to succeed. Watch the system long enough to cover the relevant workload pattern.

### Before you run it

- Run the script first on a non-production or read-only connection when possible.
- Review the complete SQL file before execution and confirm that the connected instance is the intended target.
- Required access: VIEW SERVER STATE; access to the system_health Extended Events session for deadlock XML.
- Open SQL Server Management Studio or Azure Data Studio, connect to the instance, open the downloaded file, and select **Execute**. Do not run diagnostic scripts through an application login.
- Save the result grid with the server name, collection time, and incident window. DMV output changes over time and often resets after a SQL Server restart.

### What the script does

Returns active blockers and waiters, a blocking hierarchy, current SQL text, and recent deadlock graphs from system_health. The download is intended for diagnosis and does not apply an automatic remediation. Read every statement anyway, especially when adapting the script for automation or a different SQL Server version.
