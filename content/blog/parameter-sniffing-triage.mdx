Start with actual vs estimated rows for the bad plan, then compare sniffed parameters for good and
bad executions.

Only then decide between recompile hints, optimized plan forcing, or query store plan regression
controls. Blind `OPTION (RECOMPILE)` everywhere is not a strategy.

## Why parameter sensitivity deserves a method

The central principle is that one cached plan may not serve selective and broad parameter values equally well. A single metric, recommendation, or successful command is not enough. The decision has to connect an observed symptom to a plausible cause, a controlled change, and a result that can be verified under the workload that matters.

## Evidence to collect

Use evidence from the same time window whenever possible:

- Query Store plan and runtime variation
- data skew and histogram coverage
- estimated versus actual rows
- compile and execution frequency

## A practical workflow

1. Reproduce fast and slow parameter classes.
2. Confirm that the plan difference explains the cost.
3. Choose the narrowest mitigation.
4. Monitor plan and runtime behavior after the change.

## Common mistakes

Avoid these shortcuts:

- adding RECOMPILE everywhere
- optimizing for one convenient value
- confusing blocking or resource pressure with plan sensitivity

## Verification and completion

Define completion before making the change. Confirm correctness first, then compare latency, throughput, reads, CPU, waits, storage behavior, or recovery time as appropriate for **Parameter sniffing triage in five minutes**. Test negative and boundary cases, not only the path expected to succeed. Watch the system long enough to cover the relevant workload pattern.

### Before you run it

- Run the script first on a non-production or read-only connection when possible.
- Review the complete SQL file before execution and confirm that the connected instance is the intended target.
- Required access: VIEW SERVER STATE.
- Open SQL Server Management Studio or Azure Data Studio, connect to the instance, open the downloaded file, and select **Execute**. Do not run diagnostic scripts through an application login.
- Save the result grid with the server name, collection time, and incident window. DMV output changes over time and often resets after a SQL Server restart.

### What the script does

Surfaces high-cost cached plans and plan-cache evidence that can help identify unstable estimates, reuse patterns, and parameter-sensitive workload behavior. The download is intended for diagnosis and does not apply an automatic remediation. Read every statement anyway, especially when adapting the script for automation or a different SQL Server version.
