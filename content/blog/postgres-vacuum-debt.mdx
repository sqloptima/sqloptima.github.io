Vacuum debt rarely announces itself with a single alert.

Track dead tuple ratios, freeze age, and wraparound risk. Couple that with index bloat signals so
maintenance is scheduled against evidence, not folklore.

## Why vacuum health deserves a method

The central principle is that vacuum debt grows when dead tuples accumulate faster than autovacuum can reclaim and freeze them. A single metric, recommendation, or successful command is not enough. The decision has to connect an observed symptom to a plausible cause, a controlled change, and a result that can be verified under the workload that matters.

## Evidence to collect

Use evidence from the same time window whenever possible:

- dead tuple trend and table churn
- autovacuum run frequency and duration
- old transactions and replication slots
- XID age, bloat, and storage growth

## A practical workflow

1. Find the relations accumulating debt.
2. Remove blockers such as old transactions.
3. Tune thresholds and cost settings for the table.
4. Verify that vacuum keeps pace with new churn.

## Common mistakes

Avoid these shortcuts:

- running VACUUM FULL as routine maintenance
- tuning global settings for one hot table
- ignoring long transactions and retained slots

## Verification and completion

Define completion before making the change. Confirm correctness first, then compare latency, throughput, reads, CPU, waits, storage behavior, or recovery time as appropriate for **Postgres vacuum debt compounds quietly**. Test negative and boundary cases, not only the path expected to succeed. Watch the system long enough to cover the relevant workload pattern.

### What it does

Returns live and dead tuple estimates, vacuum and analyze timestamps, modification count, XID age, relation size, a review status, and long-running transactions. The script is diagnostic and does not apply an automatic remediation. Result values still need workload context, a second supporting signal, and a before-and-after comparison.
