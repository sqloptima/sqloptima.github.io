Most “mysterious” production failures after a deploy are schema drift wearing a costume.

Compare procedures, indexes, and table definitions before cutover. Approve destructive diffs
explicitly. Keep the interactive Schema Compare tab as the UX reference for what good looks like.

## Why schema drift deserves a method

The central principle is that unreviewed differences between environments make releases unpredictable and recovery harder. A single metric, recommendation, or successful command is not enough. The decision has to connect an observed symptom to a plausible cause, a controlled change, and a result that can be verified under the workload that matters.

## Evidence to collect

Use evidence from the same time window whenever possible:

- object definitions and dependencies
- migration history and deployment artifacts
- permissions and configuration differences
- application version compatibility

## A practical workflow

1. Choose a source of truth.
2. Compare before every release.
3. Separate safe scripts from manual actions.
4. Verify the target after deployment.

## Common mistakes

Avoid these shortcuts:

- editing production objects directly
- generating destructive scripts without review
- comparing names without normalized definitions

## Verification and completion

Define completion before making the change. Confirm correctness first, then compare latency, throughput, reads, CPU, waits, storage behavior, or recovery time as appropriate for **Schema drift is a reliability problem**. Test negative and boundary cases, not only the path expected to succeed. Watch the system long enough to cover the relevant workload pattern.

### Before you run it

- Review every statement and confirm the connection points to the intended SQL Server database server.
- Run through a non-production or read-only diagnostic account first when possible.
- Required access: VIEW DEFINITION on the target database objects.
- Save the output with the server name, database name, collection time, and workload window so another engineer can reproduce the analysis.

### What it does

Returns object and expression dependencies that help define the blast radius of a schema difference. The script is diagnostic and does not apply an automatic remediation. Result values still need workload context, a second supporting signal, and a before-and-after comparison.

<details className="sql-output-guide">
<summary>How to read the output values</summary>

Read referencing and referenced object names together. Unresolved or cross-database references need manual verification. Dependency rows do not replace a schema comparison; use them to order review and deployment and to identify consumers requiring regression tests.
