Dummy guide: treat "unused" as a hypothesis, not a verdict.

Cross-check `sys.dm_db_index_usage_stats` against a full workload window (not a quiet weekend),
then confirm the index is absent from Query Store plans and missing-index recommendations that
would recreate it.

Keep indexes that protect unique constraints or cover critical point lookups even when seek counts
look low — write amplification is the trade-off you are optimizing, not a vanity metric.

## Why index usage deserves a method

The central principle is that usage counters are clues, not a verdict, because they reset and do not capture every business cycle. A single metric, recommendation, or successful command is not enough. The decision has to connect an observed symptom to a plausible cause, a controlled change, and a result that can be verified under the workload that matters.

## Evidence to collect

Use evidence from the same time window whenever possible:

- last restart and observation window
- seeks, scans, lookups, and updates
- plans, constraints, and uniqueness
- index size and maintenance cost

## A practical workflow

1. Capture usage across a full business cycle.
2. Identify dependencies and rare critical jobs.
3. Group overlapping candidates.
4. Disable or remove cautiously with rollback and monitoring.

## Common mistakes

Avoid these shortcuts:

- dropping after a short observation
- ignoring unique constraints
- treating zero seeks as zero value

## Verification and completion

Define completion before making the change. Confirm correctness first, then compare latency, throughput, reads, CPU, waits, storage behavior, or recovery time as appropriate for **Finding used and unused indexes before you drop anything**. Test negative and boundary cases, not only the path expected to succeed. Watch the system long enough to cover the relevant workload pattern.

### Before you run it

- Run the script first on a non-production or read-only connection when possible.
- Review the complete SQL file before execution and confirm that the connected instance is the intended target.
- Required access: VIEW SERVER STATE and VIEW DATABASE STATE.
- Open SQL Server Management Studio or Azure Data Studio, connect to the instance, open the downloaded file, and select **Execute**. Do not run diagnostic scripts through an application login.
- Save the result grid with the server name, collection time, and incident window. DMV output changes over time and often resets after a SQL Server restart.

### What the script does

Reports collection-window age, active indexes, read and write activity, size, temperature, and reviewed candidates that may be write-only. The download is intended for diagnosis and does not apply an automatic remediation. Read every statement anyway, especially when adapting the script for automation or a different SQL Server version.
