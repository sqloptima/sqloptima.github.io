Dummy guide: plan forcing is a seatbelt, not a destination.

Force a known-good `plan_id` when a regression is user-visible and a proper fix (stats, index,
rewrite) cannot ship in the same window. Record the query hash, forced plan id, and expiry in
your runbook.

Revisit forced plans after the next compatibility level change, major stats update, or schema
deploy — a forced plan can become the new regression.

## Why forced-plan governance deserves a method

The central principle is that forcing a known plan can stabilize an incident but it creates an operational decision that must be monitored. A single metric, recommendation, or successful command is not enough. The decision has to connect an observed symptom to a plausible cause, a controlled change, and a result that can be verified under the workload that matters.

## Evidence to collect

Use evidence from the same time window whenever possible:

- plan history and regression timing
- runtime distribution by plan
- forcing failure status
- schema, statistics, and compatibility changes

## A practical workflow

1. Confirm the prior plan is correct and stable.
2. Record why and when it was forced.
3. Monitor execution and forcing failures.
4. Define the condition for removing the force.

## Common mistakes

Avoid these shortcuts:

- forcing without result validation
- leaving a plan forced indefinitely
- using forcing instead of fixing a repeatable root cause

## Verification and completion

Define completion before making the change. Confirm correctness first, then compare latency, throughput, reads, CPU, waits, storage behavior, or recovery time as appropriate for **When (and when not) to force a plan in Query Store**. Test negative and boundary cases, not only the path expected to succeed. Watch the system long enough to cover the relevant workload pattern.

### Before you run it

- Run the script first on a non-production or read-only connection when possible.
- Review the complete SQL file before execution and confirm that the connected instance is the intended target.
- Required access: VIEW DATABASE STATE with Query Store enabled in the current database.
- Open SQL Server Management Studio or Azure Data Studio, connect to the instance, open the downloaded file, and select **Execute**. Do not run diagnostic scripts through an application login.
- Save the result grid with the server name, collection time, and incident window. DMV output changes over time and often resets after a SQL Server restart.

### What the script does

Lists currently forced plans, runtime aggregates, force failures, failure reasons, and Query Store configuration. The download is intended for diagnosis and does not apply an automatic remediation. Read every statement anyway, especially when adapting the script for automation or a different SQL Server version.
