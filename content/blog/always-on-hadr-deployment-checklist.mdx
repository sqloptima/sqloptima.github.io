Availability Groups fail more often in the middle of the stack than in the `CREATE AVAILABILITY GROUP` statement: DNS, quorum, endpoints, firewall rules, and restore sequencing.

Work Always On as a phase-gated build. Do not create the listener until secondaries are synchronized and failover has been tested in the change window.

## Order that reduces rework

1. Infrastructure, domain, accounts, DNS, and network
2. SQL install and Always On enablement
3. WSFC validate → create → quorum
4. Endpoints and firewall
5. Backup/restore to secondaries
6. AG, join, listener
7. Failover test, monitoring, documentation

## Why Always On deployment deserves a method

The central principle is that a healthy Availability Group depends on Windows, SQL Server, networking, endpoints, backups, and application connectivity working together. A single metric, recommendation, or successful command is not enough. The decision has to connect an observed symptom to a plausible cause, a controlled change, and a result that can be verified under the workload that matters.

## Evidence to collect

Use evidence from the same time window whenever possible:

- replica readiness and synchronization state
- endpoint connectivity and permissions
- listener DNS and port reachability
- backup preference and job placement

## A practical workflow

1. Record prerequisites and recovery objectives.
2. Build and validate replicas before joining databases.
3. Test listener connectivity from an application host.
4. Rehearse planned failover and failback.

## Common mistakes

Avoid these shortcuts:

- treating synchronization as application readiness
- leaving jobs enabled on every replica
- skipping quorum and failure-domain review

## Verification and completion

Define completion before making the change. Confirm correctness first, then compare latency, throughput, reads, CPU, waits, storage behavior, or recovery time as appropriate for **Always On is a 22-phase build, not a checkbox**. Test negative and boundary cases, not only the path expected to succeed. Watch the system long enough to cover the relevant workload pattern.

### Before you run it

- Run the script first on a non-production or read-only connection when possible.
- Review the complete SQL file before execution and confirm that the connected instance is the intended target.
- Required access: VIEW SERVER STATE and access to the Always On DMVs.
- Open SQL Server Management Studio or Azure Data Studio, connect to the instance, open the downloaded file, and select **Execute**. Do not run diagnostic scripts through an application login.
- Save the result grid with the server name, collection time, and incident window. DMV output changes over time and often resets after a SQL Server restart.

### What the script does

Returns replica role and connection health, database synchronization state, log-send and redo queues, transfer rates, suspension state, last commit time, and an estimated RPO indicator. The download is intended for diagnosis and does not apply an automatic remediation. Read every statement anyway, especially when adapting the script for automation or a different SQL Server version.

Start with Sync_Health and Sync_State. A queue that grows across repeated samples matters more than one non-zero value. Compare Log_Send_Queue_KB with Log_Send_Rate_KB_s for transport pressure and Redo_Queue_KB with Redo_Rate_KB_s for secondary redo pressure. Interpret RPO in the context of synchronous or asynchronous commit.
