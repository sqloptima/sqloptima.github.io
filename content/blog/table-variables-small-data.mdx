Dummy guide: table variables are not "faster temp tables."

Use `@table` when the row count is small and predictable (config lists, id batches under a few
hundred). Prefer `#temp` when cardinality is unknown, when you need statistics-driven plans, or
when you will index intermediate results.

On modern SQL Server versions, deferred compilation helps table variables — still verify with
actual row counts before promoting a pattern across the codebase.

## Why table variable choice deserves a method

The central principle is that table variables can be effective for genuinely small intermediate sets, but row estimates and repeated access still matter. A single metric, recommendation, or successful command is not enough. The decision has to connect an observed symptom to a plausible cause, a controlled change, and a result that can be verified under the workload that matters.

## Evidence to collect

Use evidence from the same time window whenever possible:

- actual row count and variation
- compatibility level and deferred compilation
- join choices and spills
- need for indexes or statistics

## A practical workflow

1. Measure the intermediate cardinality.
2. Inspect estimates and downstream operators.
3. Compare a temporary table for larger or unstable sets.
4. Test across representative parameter values.

## Common mistakes

Avoid these shortcuts:

- using a fixed row-count rule
- assuming memory-only storage
- ignoring repeated scans and missing indexes

## Verification and completion

Define completion before making the change. Confirm correctness first, then compare latency, throughput, reads, CPU, waits, storage behavior, or recovery time as appropriate for **Table variables for small, known rowsets**. Test negative and boundary cases, not only the path expected to succeed. Watch the system long enough to cover the relevant workload pattern.
