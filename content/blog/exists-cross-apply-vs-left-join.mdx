Dummy guide: `LEFT JOIN ... WHERE child.id IS NOT NULL` is usually an existence check in disguise.

Rewrite to `EXISTS` so the engine can short-circuit after the first match. Use `CROSS APPLY`
(or `OUTER APPLY`) when you need columns from the "top 1 related row" without exploding the
parent into many child rows.

Keep true left joins when you must project nullable child columns for every parent — that is a
different problem than filtering parents that have children.

## Why relational operator choice deserves a method

The central principle is that EXISTS, APPLY, and JOIN express different result shapes and should be selected from the required semantics. A single metric, recommendation, or successful command is not enough. The decision has to connect an observed symptom to a plausible cause, a controlled change, and a result that can be verified under the workload that matters.

Start by writing down the scope. Name the instance, database, application path, business window, and user impact. Record what changed recently and what must remain unchanged. This prevents a useful investigation from turning into an unrelated cleanup exercise, and it gives reviewers a clear boundary for the work.

## Evidence to collect

Use evidence from the same time window whenever possible:

- whether only existence is needed
- whether one related row or many are returned
- duplicate behavior
- available predicates and indexes

Capture timestamps, server and database identity, relevant configuration, and the query or operation that produced the observation. Cumulative counters need a baseline or delta. Plans need their parameter and runtime context. Screenshots can help explain a result, but retain the underlying values or scripts so another engineer can reproduce the conclusion.

Do not begin with a preferred fix. First decide what evidence would confirm the suspected cause and what evidence would disprove it. That small discipline reduces confirmation bias and makes rollback decisions much easier.

## A practical workflow

1. Write the required row shape first.
2. Choose the operator that states that intent.
3. Test NULL and duplicate cases.
4. Compare plans and resource use with representative data.

Make one meaningful change at a time. Run it first in a safe environment with representative volume and distribution. Compare the same workload before and after the change, and keep the original script or configuration ready for rollback. If several changes ship together, the team loses the ability to explain which one helped or harmed the system.

For production work, record the owner, review time, execution window, expected impact, stop condition, and rollback trigger. The result should be understandable to the next engineer on call without relying on memory or chat history.

## Common mistakes

Avoid these shortcuts:

- using DISTINCT to hide join multiplication
- assuming one syntax is always faster
- changing semantics during a rewrite

These mistakes are attractive because they produce a quick action. They are risky because they detach the action from workload evidence. A change can appear successful during a quiet test and still fail under concurrency, skew, maintenance activity, or a different business cycle.

## Verification and completion

Define completion before making the change. Confirm correctness first, then compare latency, throughput, reads, CPU, waits, storage behavior, or recovery time as appropriate for **EXISTS and CROSS APPLY instead of LEFT JOIN for existence checks**. Test negative and boundary cases, not only the path expected to succeed. Watch the system long enough to cover the relevant workload pattern.

The work is complete when the evidence supports the outcome, monitoring can detect regression, and the team has a documented rollback or recovery path. If the result is inconclusive, keep the finding open and state what additional observation is needed rather than presenting an assumption as a fix.
