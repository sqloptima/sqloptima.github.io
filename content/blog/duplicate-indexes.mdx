Dummy guide: exact duplicates are easy; near-duplicates hide in INCLUDE lists.

Compare key column order first, then included columns. If index A is a strict subset of index B
and both are nonclustered, B usually wins — but verify uniqueness, filtered predicates, and
compression settings before you drop A.

Document the change in your change ticket so the next incident does not recreate the duplicate
from an old create script.

## Why index overlap deserves a method

The central principle is that duplicate and near-duplicate indexes increase storage and write cost while rarely providing equal read value. A single metric, recommendation, or successful command is not enough. The decision has to connect an observed symptom to a plausible cause, a controlled change, and a result that can be verified under the workload that matters.

## Evidence to collect

Use evidence from the same time window whenever possible:

- key columns and order
- included columns and filters
- usage since the last restart
- write rate, size, and maintenance cost

## A practical workflow

1. Inventory definitions and dependencies.
2. Group exact and overlapping candidates.
3. Check plans and critical workloads.
4. Remove one candidate at a time with a rollback script.

## Common mistakes

Avoid these shortcuts:

- dropping indexes from usage counters alone
- ignoring uniqueness or filtered predicates
- combining indexes into an excessively wide replacement

## Verification and completion

Define completion before making the change. Confirm correctness first, then compare latency, throughput, reads, CPU, waits, storage behavior, or recovery time as appropriate for **Spotting duplicate and near-duplicate indexes**. Test negative and boundary cases, not only the path expected to succeed. Watch the system long enough to cover the relevant workload pattern.

### Before you run it

- Run the script first on a non-production or read-only connection when possible.
- Review the complete SQL file before execution and confirm that the connected instance is the intended target.
- Required access: VIEW DATABASE STATE on the databases being reviewed.
- Open SQL Server Management Studio or Azure Data Studio, connect to the instance, open the downloaded file, and select **Execute**. Do not run diagnostic scripts through an application login.
- Save the result grid with the server name, collection time, and incident window. DMV output changes over time and often resets after a SQL Server restart.

### What the script does

Compares index keys, included columns, filters, constraints, size, and usage to identify exact and near-duplicate candidates. The download is intended for diagnosis and does not apply an automatic remediation. Read every statement anyway, especially when adapting the script for automation or a different SQL Server version.
