Filter to queries whose average duration or CPU jumped across the change window, open the plan

If the new plan is consistently worse, force the prior plan only after you understand *why* the
optimizer flipped — otherwise you paper over a stats or index problem that will return.

## Why regression investigation deserves a method

The central principle is that Query Store helps separate a code regression from a plan change by preserving historical runtime and plan evidence. A single metric, recommendation, or successful command is not enough. The decision has to connect an observed symptom to a plausible cause, a controlled change, and a result that can be verified under the workload that matters.

## Evidence to collect

Use evidence from the same time window whenever possible:

- duration, CPU, and reads by interval
- plan ids and first-use time
- execution count and parameter variation
- deployments and statistics events

## A practical workflow

1. Define the regression window.
2. Compare plans and runtime distributions.
3. Reproduce the responsible parameter class.
4. Mitigate, validate, and continue monitoring.

## Common mistakes

Avoid these shortcuts:

- sorting only by total duration
- comparing unequal time windows
- forcing a plan before checking data and schema changes

## Verification and completion

Define completion before making the change. Confirm correctness first, then compare latency, throughput, reads, CPU, waits, storage behavior, or recovery time as appropriate for **Catching regressed queries with Query Store**. Test negative and boundary cases, not only the path expected to succeed. Watch the system long enough to cover the relevant workload pattern.
