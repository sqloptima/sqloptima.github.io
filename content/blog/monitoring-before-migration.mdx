Capture slow queries, throughput, and wait profiles before changing engines.

Migration success is easier to defend when you can show before/after reliability metrics.

## Why migration baselines deserves a method

The central principle is that source monitoring defines what the target must support and which problems should not be migrated unchanged. A single metric, recommendation, or successful command is not enough. The decision has to connect an observed symptom to a plausible cause, a controlled change, and a result that can be verified under the workload that matters.

## Evidence to collect

Use evidence from the same time window whenever possible:

- throughput, latency, and concurrency
- top queries and workload windows
- growth, backup, and maintenance patterns
- availability and recovery behavior

## A practical workflow

1. Capture several representative business cycles.
2. Separate normal peaks from incidents.
3. Map source signals to target controls.
4. Retain the baseline for post-cutover comparison.

## Common mistakes

Avoid these shortcuts:

- sizing from allocated storage alone
- capturing only an average day
- discarding the source baseline after cutover

## Verification and completion

Define completion before making the change. Confirm correctness first, then compare latency, throughput, reads, CPU, waits, storage behavior, or recovery time as appropriate for **Monitor before you migrate**. Test negative and boundary cases, not only the path expected to succeed. Watch the system long enough to cover the relevant workload pattern.

### Before you run it

- Review every statement and confirm the connection points to the intended SQL Server database server.
- Run through a non-production or read-only diagnostic account first when possible.
- Required access: VIEW SERVER STATE.
- Save the output with the server name, database name, collection time, and workload window so another engineer can reproduce the analysis.

### What it does

Captures a repeatable point-in-time workload and resource baseline before migration. The script is diagnostic and does not apply an automatic remediation. Result values still need workload context, a second supporting signal, and a before-and-after comparison.
