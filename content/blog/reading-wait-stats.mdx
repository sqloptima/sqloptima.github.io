Start with waits that correlate to application timeouts, not every counter that moved.

Sort by cumulative wait time, exclude benign noise (like `SLEEP_TASK`), and pair the top
waiters with a slow-query sample from the same window.

SQLOptima Monitoring surfaces this pairing so DBAs can move from symptom to statement faster.

## Why wait-stat analysis deserves a method

The central principle is that waits describe where sessions spend time, but interpretation requires a time window and workload context. A single metric, recommendation, or successful command is not enough. The decision has to connect an observed symptom to a plausible cause, a controlled change, and a result that can be verified under the workload that matters.

## Evidence to collect

Use evidence from the same time window whenever possible:

- delta waits over the incident period
- signal wait versus resource wait
- throughput and concurrency
- queries and resources active in the same window

## A practical workflow

1. Capture a baseline and a focused delta.
2. Group waits by resource category.
3. Correlate the leading category with other evidence.
4. Investigate the responsible workload before tuning.

## Common mistakes

Avoid these shortcuts:

- tuning from lifetime totals
- treating benign idle waits as incidents
- mapping one wait type directly to one fix

## Verification and completion

Define completion before making the change. Confirm correctness first, then compare latency, throughput, reads, CPU, waits, storage behavior, or recovery time as appropriate for **Reading wait stats without drowning in noise**. Test negative and boundary cases, not only the path expected to succeed. Watch the system long enough to cover the relevant workload pattern.

### Before you run it

- Run the script first on a non-production or read-only connection when possible.
- Review the complete SQL file before execution and confirm that the connected instance is the intended target.
- Required access: VIEW SERVER STATE.
- Open SQL Server Management Studio or Azure Data Studio, connect to the instance, open the downloaded file, and select **Execute**. Do not run diagnostic scripts through an application login.
- Save the result grid with the server name, collection time, and incident window. DMV output changes over time and often resets after a SQL Server restart.

### What the script does

Filters common idle waits and returns the top 25 wait types with task count, total, resource and signal wait seconds, average wait, percentage, and a first-line recommendation. The download is intended for diagnosis and does not apply an automatic remediation. Read every statement anyway, especially when adapting the script for automation or a different SQL Server version.
