Rank by blast radius, not by how interesting the finding is. SQLOptima Assessment is designed to

## Why assessment follow-through deserves a method

The central principle is that an assessment creates value only when findings become owned, testable work. A single metric, recommendation, or successful command is not enough. The decision has to connect an observed symptom to a plausible cause, a controlled change, and a result that can be verified under the workload that matters.

## Evidence to collect

Use evidence from the same time window whenever possible:

- severity and business impact
- evidence that reproduces the finding
- the affected server, database, or workload
- a measurable remediation outcome

## A practical workflow

1. Normalize findings into a backlog.
2. Separate urgent risk from planned improvement.
3. Add acceptance and rollback criteria.
4. Review closure evidence with the owner.

## Common mistakes

Avoid these shortcuts:

- copying report text without context
- creating one oversized remediation ticket
- closing work without a verification result

## Verification and completion

Define completion before making the change. Confirm correctness first, then compare latency, throughput, reads, CPU, waits, storage behavior, or recovery time as appropriate for **Assessment reports should drive tickets**. Test negative and boundary cases, not only the path expected to succeed. Watch the system long enough to cover the relevant workload pattern.

### Before you run it

- Review every statement and confirm the connection points to the intended SQL Server database server.
- Run through a non-production or read-only diagnostic account first when possible.
- Required access: VIEW SERVER STATE and read access to system metadata.
- Save the output with the server name, database name, collection time, and workload window so another engineer can reproduce the analysis.

### What it does

Collects configuration, workload, storage, backup, and operational evidence suitable for assessment findings. The script is diagnostic and does not apply an automatic remediation. Result values still need workload context, a second supporting signal, and a before-and-after comparison.
