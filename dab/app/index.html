From prompt to production with SQL Server and Data API Builder

Use GitHub Copilot to accelerate SQL work, then expose approved database operations through Data API Builder without handing an AI client raw database access.

By Ravi SharmaSeptember 26, 202612 minute read

AI can shorten the path from a requirement to working SQL. It does not shorten the list of engineering responsibilities. The useful workflow gives Copilot the right context, reviews every proposed change, measures the result in SQL Server, and exposes only approved operations through a governed API.

This article turns that workflow into a practical architecture. GitHub Copilot supports development inside the repository. Data API Builder, or DAB, publishes configured tables, views, and stored procedures through REST, GraphQL, and MCP. SQL Server remains the system of record.

Copilot belongs inside a reviewable workflow

Copilot works best when it can see the schema, repository conventions, target files, SQL dialect, and acceptance criteria. A useful prompt states the expected inputs and outputs, names the SQL Server version when it matters, and explains the constraints that must remain true.

  1. Ground the request. Open the repository, attach the relevant schema and SQL, and include the conventions that govern the change.
  2. Ask for a focused change. Name the target file, expected result, constraints, and test conditions.
  3. Inspect the proposal. Check object names, assumptions, parameter handling, security, and unrelated edits.
  4. Validate with evidence. Run the SQL against development data. For performance work, compare execution plans, logical reads, CPU, duration, and result correctness.
  5. Iterate with exact feedback. Give Copilot the real error or measurement rather than asking it to guess what failed.
One rule matters more than the rest: Copilot proposes. SQL Server measures. The developer decides. A claimed speed improvement without a measured baseline is not a result.

Repository instructions make the output more consistent

Keep short, recurring rules in .github/copilot-instructions.md. This is a sensible home for the SQL dialect, safe input patterns, repository conventions, expectations for focused edits, and a clear rule that prompts must not contain secrets or production data.

Use task-specific skills for detailed guidance that only applies to certain work, such as query review, schema changes, migrations, performance analysis, or DAB configuration.

The production boundary should not be raw SQL

An AI client needs a narrow contract, not unrestricted database credentials. DAB creates that boundary by mapping selected database objects to named operations and applying configured permissions before a request reaches SQL Server.

The application still owns the user experience, specialized validation, retries, and cross-system workflows. The platform still owns identity, secrets, networking, telemetry, deployment, and backups. The database team still owns schema design, keys, constraints, indexes, permissions, and migrations.

Traditional API and DAB side by side

A custom API remains the right choice when the contract must stay independent of the database model or when a workflow spans several systems. For predictable entity CRUD, DAB can remove a large amount of repeated plumbing.

Traditional Express API

Flow: browser → routes → validation and permissions → database driver → SQL Server

  • Write GET, POST, PATCH, and DELETE routes.
  • Maintain SQL or ORM mappings.
  • Implement response models, error handling, tests, and API documentation.
  • Coordinate permissions across each access path.

Data API Builder

Flow: browser or AI client → configured endpoint → entity permissions → SQL Server

  • Map an entity to an approved table, view, or procedure.
  • Configure roles, actions, visible fields, and row policies.
  • Expose a consistent contract through REST, GraphQL, and MCP.
  • Keep the database connection behind the service.
"Task": {
  "description": "Workshop tasks for governed CRUD",
  "source": { "object": "dbo.Tasks", "type": "table" },
  "permissions": [{
    "role": "reader",
    "actions": ["read"]
  }],
  "rest": { "path": "tasks" }
}

Where DAB fits, and where it does not

DAB works well for CRUD applications, internal tools, admin portals, mobile and web backends, rapid prototypes with a production path, and AI clients that need named SQL operations. A hybrid design often works best when a product combines ordinary entity access with complex business workflows.

DAB does not design the database, replace domain logic, orchestrate long-running work, or provide a complete security program. It also does not make every database object available automatically. Teams choose the objects and operations that enter the contract.

A safe production result is reviewed and tested SQL behind governed access.

Five checks before a request reaches SQL Server

  1. Authenticate the caller. Use an appropriate identity provider in production.
  2. Select the effective role. The role determines which configured entities the caller can discover.
  3. Authorize the action. Read, create, update, delete, and execute remain separate grants.
  4. Restrict fields and rows. Field lists and policies reduce the data returned or changed.
  5. Protect the database. Retain least-privilege database permissions, constraints, auditing, and row-level security where required.

A practical starting sequence

Generate the initial configuration with the DAB command line, review the result, validate it, and then start the service. Keep connection strings in environment variables or a managed secret store.

dab init --database-type mssql ...
dab add Task --source dbo.Tasks --permissions "reader:read"
dab update Task --description "Approved workshop tasks"
dab configure --runtime.mcp.enabled true
dab validate --config dab-config.json
dab start --config dab-config.json

Before production, inspect the configuration diff, confirm every role and action, test allowed and denied requests, and verify that each exposed field is intentional. AI can help draft the configuration. It should not approve its own privileges.
